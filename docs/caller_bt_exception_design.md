# 天通模块 (GMR MES) 与 iOS App 蓝牙链路异常处理集成架构

**目标受众:** iOS App 开发者 / AI 辅助开发助手
**核心目标:** 在 BLE 与卫星模块通信的场景下，通过严密的本地状态机与容错逻辑，解决链路脆弱性带来的状态不同步与边缘异常。

---

## 一、 核心状态映射与流程设计

* **状态对齐原则:** 必须将 `^DSCI` 的 7 种状态（Active, Holding, MO, Alerting, MT, Waiting, End）严格映射到 `CXProvider` 的状态中。
* **关键信令补充:** 引入 `^ORIG` (发起指示)、`^CONF` (承载连通)、`^CONN` (对方接听) 作为底层心跳，补充 `^DSCI` 状态更新的间隙。

---

## 二、 边缘场景处理策略

针对 BLE 的不稳定性与高延迟卫星链路，必须实施以下处理策略：

### 1. 拨号/通话中的 BLE 重连恢复
* **状态记录:** BLE 断开时，App 保留当前的 `CallID` 和通话阶段。
* **恢复机制:** BLE 重连后，第一时间执行 `AT+CLCC` 校验。若通话仍存续，则静默恢复音频路由与 UI 状态；若底层已挂断，则同步清理资源。

### 2. 蓝牙连通后的“状态倒挂”修正 (Hot-Sync)
* **场景描述:** 硬件端独立拨号/接听后才建立 BLE 连接。
* **处理策略:** 启动 GATT 后执行 `AT+CLCC` 强制拉取底层真实状态。若模块存在 `Active` 呼叫而本地无记录，则触发 CallKit 静默插入机制，重新建立音频通道，避免“幽灵通话”或系统无法管理的问题。

### 3. “幽灵通话”与异常断连处理
* **清理逻辑:** 通过定时轮询 `AT+CLCC` 校验状态的一致性。若发现列表为空但本地显示通话中，调用 `CXProvider.reportCall` 销毁实例；若 UI 已挂断但模块端仍有 Active 记录，立即补发 `AT+CHUP` 掐断链路，防止计费异常。

### 4. 断接原因分析
* 利用 `^DSCI` 状态 6 结尾的 `<cause>` 字段 进行降级处理：
    * `16`：正常挂断。
    * `17`：用户忙，提示用户。
    * `31`：链路掉线，告知用户卫星信号波动风险。

## 三、 Swift 开发注意事项

为了确保工程的健壮性，在 Swift 实现中必须严格遵循以下原则：

1.  **串口解析与分发 (Parser Architecture):**
    * **独立处理:** 串口接收器 (Serial Receiver) 必须将 **URC 主动上报** (以 `^` 或 `+` 开头，如 `^DSCI`、`^CONN`) 与 **指令响应** (`OK` / `ERROR`) 逻辑分离。避免响应处理干扰状态机的自动流转。
2.  **状态机幂等处理 (Idempotency):**
    * **防抖机制:** 在 `CallStateMachine` 中，对同一个 `CallID` 的状态变更必须具备幂等性。若当前呼叫已处于 `Active` 状态，必须丢弃重复到达的 `^CONN` 或 `^DSCI` 报文，防止 CallKit 密集更新导致触发系统 Exception。
3.  **AT 指令竞态控制:**
    * **任务队列:** 将 `ATD`、`ATA`、`AT+CHUP` 等控制指令放入串行队列 (Serial Queue) 执行，并设立 **2000ms - 3000ms 的超时守护定时器**。一旦超时未收到期望的响应，优先探测模块存活状态，最大尝试 1 次重试。
4.  **Audio Session 恢复优化:**
    * **路由重建:** 每次 BLE 断连恢复或通话状态同步时，必须手动检查 `AVAudioSession` 的路由配置，确保音频成功流向蓝牙硬件，而非回落到手机扬声器。
5.  **强制清理兜底:**
    * 在任何极端混乱状态（如状态机计数溢出、通信完全无法对齐）下，应提供“强力重置”按钮，发送 `AT+CHUP` 后执行 `Modem Reset` 指令，将天通模块恢复至初始空闲状态。
